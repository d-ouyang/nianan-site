# v0.5.2 · 关于屏流体静默失效修复（WebGL 上下文独占挂载）

> 关联版本：0.5.2（0.5.1 的 PATCH）
> 关联计划：P0-4b·补 后续修复
> 一句话结论：**关于屏的 SplashCursor 一直没有任何效果、且零报错，根因是「多 WebGL2 上下文同时常驻」导致后挂载的特效拿不到可用的渲染目标、直接 no-op；修复方式是按当前屏独占挂载，任一时刻最多一个重负载 WebGL2 特效存活。**

## 1. 现象与诉求

- 用户：鼠标流体特效在「关于」屏「没有任何效果」。首屏（Hero）在 0.5.1 把 splat 可见度从 0.15 提到 0.42 后已基本可见，但关于屏始终空白。
- 难点的核心：**特效静默失效、控制台零报错**，常规排查（色值、挂载位置、事件绑定）都看不出问题。

## 2. 根因

提交 0.5.1 后，页面同时存在 **3 个长期存活的 WebGL2 上下文**：

1. Hero 的 `MicroSlats`（ogl，始终挂载）
2. Hero 的 `SplashCursor`（0.5.0 加在 Hero 内）
3. 关于屏的 `SplashCursor`（0.5.1 加在 Stub/about）

Hero 的两个上下文只是「离屏暂停 rAF」，但**上下文及其 float 渲染目标（RGBA16F/RG16F/R16F 的 FBO）一直不释放**。当滚到关于屏时，关于屏的 SplashCursor 是第 3 个上下文，在 GPU 上下文资源受限的机器（集成显卡 / ANGLE / SwiftShader）上，后挂载的上下文在 `getSupportedFormat` 探测 float 渲染目标时失败，代码优雅降级到 8-bit 仍失败，最终 `getWebGLContext` 直接 `return null` 且不抛错 —— 表现就是「空白 + 无报错」。

诊断证据（headless SwiftShader 复现）：`checkFramebufferStatus` 返回 `36061`（FRAMEBUFFER_UNSUPPORTED），对 **RGBA8/UNSIGNED_BYTE 这种最基础格式也报不支持**，说明不是 shader 问题，而是该上下文已被资源限制卡死；同时日志里 `getWebGLContext` 被调用了两次（两个 SplashCursor 实例并存），印证多上下文争抢。

## 3. 否掉的方案 + 代价

- ❌ **只在 SplashCursor 里加 8-bit 降级 / 报错日志**：治标。多上下文争抢下，连 RGBA8 都拿不到，降级救不了；日志也只在出问题时刷屏，不解决「关于屏没效果」。
- ❌ **干脆给 SplashCursor 单屏全局挂载成 fixed 背景**：会改变「流体只在关于屏」的设计意图，且仍可能与 Hero 的 MicroSlats 并存（2 个上下文）。
- ✅ **按当前屏独占挂载（采用）**：把 WebGL 背景的挂载与 `useScrollSystem` 返回的 `active` 区块绑定。任一时刻最多一个重负载 WebGL2 特效存活，关于屏滚动到时独占 GPU，Hero 滚走时其上下文随组件卸载 `loseContext()` 释放。代价：滚回 Hero 需要重建一次 WebGL 上下文（仅发生在屏间切换，可接受）。

## 4. 改动

- `src/components/sections/Hero.tsx`：接收 `active` prop；`MicroSlats + SplashCursor` 仅在 `active === 'hero'` 时挂载，否则走 `StaticGlow` 静态降级。
- `src/components/sections/Stub.tsx`：`SplashCursor` 仅在 `fluid && canRunWebGL() && active === id` 时挂载（关于屏）。
- `src/App.tsx`：把 `active` 透传给 `Hero` 与 `Stub`。
- `src/components/bits/SplashCursor.tsx`：移除调试用的 `[dbg] FBO incomplete` 控制台日志（保留 8-bit 降级说明与「真不支持」的 `console.warn`）。

## 5. 验证

Playwright（headless + SwiftShader）统计页面 canvas（即 WebGL 上下文）数量：

| 位置 | `.micro-slats canvas` | `#splash-cursor` | 合计 |
|---|---|---|---|
| Hero（active） | 1 | 1 | 2 |
| 关于（active） | 0 | 1 | **1** |
| 滚回 Hero | 1 | 1 | 2 |

关于屏从「3 个上下文」降到「1 个上下文」，且 Hero 滚走后其 canvas 真的被卸载（滚回又能重建，证明不是单向泄漏）。同时原先的 `FRAMEBUFFER_UNSUPPORTED` / 「不支持渲染目标」警告消失——即便在 headless 软件渲染下，独占单上下文也能成功初始化。真实 GPU（用户机器）下，关于屏流体必出。

> 注：headless SwiftShader 的 render-to-texture 本身有缺陷，无法用 `readPixels` 验证墨点像素；本验证以「上下文数量 / 挂载卸载」为准，最终观感仍需用户在真实浏览器确认。

## 6. 复盘与遗留

- 「静默失效 + 零报错」的特效，第一直觉应是**资源/上下文限制**而不是 shader 逻辑；SplashCursor 这类 Pavel Dobryakov 流体库会优雅 `return null`，要主动加诊断。
- 多 WebGL 上下文是这类站点最常见的坑：每个全屏 shader 都是一个上下文，叠加必炸。后续任何新加的 WebGL 背景都走「`active` 独占挂载」这套，别再各自常驻。
- 遗留：如果用户机器上 Hero 的 2 个上下文（MicroSlats + SplashCursor）也偏吃力，可考虑 Hero 只保留 MicroSlats、把鼠标流体只留给关于屏（那样全站恒为 1 个上下文）。待用户真机反馈再定。
